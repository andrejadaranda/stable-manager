# Internationalisation

Longrein uses [next-intl](https://next-intl.dev). The infrastructure is
in place and proven end-to-end; **most of the UI has not been migrated
yet**. See "What's left" below before assuming a screen is translatable.

## How it works

| File | Role |
|---|---|
| `i18n/config.ts` | The locale list, the cookie name, and why routing is un-prefixed |
| `i18n/request.ts` | Resolves the locale per request and loads its messages |
| `i18n/actions.ts` | Server action behind the language switcher |
| `messages/en.json`, `messages/lt.json` | The strings |
| `components/i18n/language-switcher.tsx` | The switcher (server component, no client JS) |

Locale resolution order: the `NEXT_LOCALE` cookie → `Accept-Language` →
English.

### No locale in the URL

There is no `/en/dashboard` or `/lt/login`. This is a deliberate
departure from next-intl's documented default, argued in full at the top
of `i18n/config.ts`. The short version: prefixed routing would have meant
moving all 85 pages under `app/[locale]/`, and would silently break the
SEO rules in `next.config.js`, the auth guard in `middleware.ts`, and
every share link already sitting in a customer's inbox.

The trade-off accepted in exchange: a page cannot be linked in a specific
language.

## Using it

**Server components** — the default, and preferred:

```tsx
import { getTranslations } from "next-intl/server";

export default async function Page() {
  const t = await getTranslations("auth.login");
  return <h1>{t("heading")}</h1>;
}
```

**Client components** — only where one is already needed:

```tsx
"use client";
import { useTranslations } from "next-intl";

export function Form() {
  const t = useTranslations("auth.login");
  return <button>{t("submit")}</button>;
}
```

Message keys are namespaced by area (`auth.login.heading`). Keep the
namespace matching the feature folder so a translator can find every
string for one screen in one block.

## Adding a language

1. Add the code to `LOCALES` and a label to `LOCALE_LABELS` in `i18n/config.ts`.
2. Copy `messages/en.json` to `messages/<code>.json` and translate it.

Nothing else — the switcher and the request config both read from
`LOCALES`.

## What's left

Currently translated: the login screen (`app/(auth)/login/page.tsx`,
`components/auth/login-form.tsx`) and the switcher itself — **3 files out
of 272** with user-facing text.

Everything else still has English written directly into the JSX. That is
not a bug to file, it is the remaining work, and it is genuinely large:
roughly 85 pages and 180 components.

A sensible order, most-valuable first:

1. **The rest of the auth flow** — signup, forgot-password, the
   confirmation screens. Small, self-contained, and it's what a
   prospective customer sees before they trust us with a card.
2. **Public and shared pages** — `/legal/*`, `/s/[slug]`, `/invite/*`,
   `/live/*`. These get sent to people who never log in, including horse
   owners and parents who may not read English.
3. **The dashboard shell** — navigation, page headers, empty states.
   High visibility per string translated.
4. **Feature screens** — clients, horses, calendar, finance. The long
   tail; do it a folder at a time.
5. **Server-side strings** — validation messages and email copy in
   `lib/` and `services/`. Easy to forget because they aren't in a
   component, and very visible when they're wrong.

Two things not yet handled, worth deciding on before the long tail:

- **Dates and currency.** There are 83 raw `toLocaleDateString` calls.
  next-intl's `useFormatter` would route these through the active locale
  and the pinned `Europe/Vilnius` time zone instead of the browser's
  guess.
- **Plurals.** English "1 lesson / 2 lessons" is two forms; Lithuanian
  has three (`1 pamoka`, `2 pamokos`, `10 pamokų`) with a rule that
  depends on the last two digits. Any counted noun needs ICU plural
  syntax rather than string concatenation — `{count, plural, one {...}
  few {...} other {...}}`.

## Tests

`e2e/public/i18n.spec.ts` covers the default language, switching,
persistence across a reload, and `Accept-Language` detection. Extend it
rather than trusting a manual click when you touch locale resolution.
